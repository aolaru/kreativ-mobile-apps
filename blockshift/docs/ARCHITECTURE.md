# Architecture and invariants

## Presentation pipeline in 0.3.0

GameSession still commits every transaction synchronously. The UI controller captures outgoing cell colors around a successful placement or shift and passes presentation data to BoardEffects. That object owns a bounded timeline, motion/landing snapshots, clear ghosts, line sweeps, reward text and particles; it never writes to GameSession or its RNG. GameCanvas draws authoritative board state beneath transient overlays and uses one two-layer tile material for whole tiles and cropped wrap fragments. New pickup/selection or modal navigation cancels old overlays, and processing stops at idle. Reduced motion eliminates the timeline; Zen removes particles; battery saver reduces the particle budget.

Timings and particle budgets live in config/visuals.json. Atmosphere draws cached small gradients without an idle update loop. Tile, sheen, primary-button, hero and completion-badge SVGs are original source assets. Graphical tests compare placed/empty footprints and record actual renderer phases using isolated saves and a controlled effect clock. Generated previews are guarded by build/.gdignore and explicit export exclusions.

`Board` owns exactly 64 color IDs (0 empty, 1–4 occupied). It validates an entire placement before mutation and clears the union of completed rows and columns. `PieceGenerator` owns one seeded RNG; palette IDs are derived from catalog IDs. Its catalog and scoring configuration are project data rather than UI constants.

`GameSession.place()` and `.move_line()` are the sole public gameplay mutations. The session commits a placement/shift, resolves all lines at once, awards score, earns energy, refills a used hand, then checks daily completion or no-move game over. Zen replaces a stranded board. Sessions reject moves after completion. A shift validates charge, mode, axis, index, direction and actual board change; only success spends the charge. A single action is synchronous and reentrant input cannot observe a partially animated transaction.

`GameCanvas` maps pointer position to shape origin using shape bounds, a fixed logical finger lift and board cell size. One touch ID owns a drag; synthetic mouse events are ignored on the canvas, while mouse emulation allows native buttons to receive touch. Touch cancellation, pause, focus loss and navigation release pointer ownership. Board preview simulates line completion on a copy. Drop and wrap animation retain only visual snapshots and expire within fractions of a second. Reduced motion bypasses these animations.

`SaveManager` validates envelopes, migrates v1/v2 data to version 3 and rejects future-version writes. File order is: write temp → flush/close → verify checksum → rotate valid main to backup → rename temp to main. Startup checks all three by sequence so interruption between renames still leaves recovery material. A damaged main is never rotated over a good recovered backup. Settings are sanitized. Session restore reconstructs pieces from catalog IDs instead of trusting arbitrary serialized shapes, restores the RNG state as a decimal string (avoids JSON integer precision loss), validates board colors and derives completion/no-move state again.

Each saved mode checkpoint supplies its own previously accounted lines/playtime. Repeated checkpoints add only deltas, including after switching modes. Starting a new run clears only that mode slot and increments its game count once. The canonical save contains runs keyed by mode and a last_mode pointer; there is no duplicated active snapshot. Tutorial/editor QA bypass statistics and run writes. Mode selection resumes saved boards by default; explicit New game asks before replacing that mode. Older interrupted Dailies can resume at their locked date or be explicitly replaced by today’s challenge.

`MonetizationManager` is a policy boundary, not an SDK. Its purchase and ad adapters always report unavailable. A future billing adapter must verify store purchase ownership and acknowledgment before publishing a PRO entitlement, restore purchases, handle pending/canceled/refunded transactions and provide store-localized pricing. No entitlement is inferred from a price button or local Boolean. An ad adapter must remain uninitialized until the applicable consent flow permits it. Interstitial eligibility requires an inactive game, no tutorial, four finished games, four minutes elapsed, spacing, consent and no verified PRO. The disabled adapter means these calls cannot display ads in this build. Rewarded ads are optional and currently have no gameplay reward integration.

UI navigation is implemented by `main.gd`; the core does not know about nodes, tweens, audio, clocks, operating-system APIs, SDKs or files. Daily date acquisition is the only calendar boundary and its seed function is pure. This keeps future iOS adapters and modes independent of rendering.

Menus run at 30 FPS and gameplay at 60 FPS. Android does not use Godot low-processor mode: a cold-start smoke test showed that it could leave scene timers waiting for the next touch. Static processing is kept small; the board only animates during brief feedback windows. Navigation hides and queues old controls for deletion so event targets remain in the tree until native input dispatch finishes.

Android system Back is routed through the root Window’s `go_back_requested` signal, with `SceneTree.quit_on_go_back` disabled. During a run it opens Pause rather than using Godot’s default mobile exit. This path is exercised by the UI harness and the emulator’s real Back key. See the [Godot SceneTree reference](https://docs.godotengine.org/en/stable/classes/class_scenetree.html).

## Configuration and navigation in 0.2.0

SettingsManager validates numeric ranges and nonfinite inputs, supplies defaults for older saves, exposes the game frame budget and restores preferences without erasing tutorial completion. GameCanvas uses one configurable lift calculation for held geometry, preview validation and landing. It fits the board and hand as one group and scales tray shapes in both dimensions. UI pages own a Back callable; modal sheets take priority, and a short duplicate-event guard protects Android devices that deliver a window request plus a cancel key for one press. Settings restore changes presentation preferences only; GameSession transactions remain unchanged.

The graphical test runner generates review/android-layout.json through a separate isolated test scene. The dedicated emulator harness uses those measured control points instead of copied coordinates and checks its version against the APK. Neither tests nor fixtures are included in Android builds.

## SHIFT continuation and preview in 0.4.0

ShiftSystem.preview copies a board, shifts, resolves lines and checks remaining pieces without touching game state, score, energy or RNG. GameSession uses the same preview for both UI prediction and terminal-state decisions. If pieces are blocked, a charged rescuing move keeps the run active. A continuation may also complete Daily; a clear that recharges SHIFT can be followed by another rescue. Recursive continuation search only recurs after charge-replenishing clears, so occupied cells strictly decrease. Invalid/unhelpful moves on a blocked board cannot spend the charge. Completed historical snapshots retain their terminal flag.

Direction buttons and swipes create previews. The canvas draws the shifted board, marks future clears and labels future-fitting pieces. Apply commits exactly once; Cancel discards presentation state. Piece dragging is disabled while a SHIFT preview is armed. Risky ordinary moves remain available with an explicit game-over warning. The blocked state suggests one rescuing move automatically and Pause offers End this run.

Save format version 3 and gameplay/Daily rule version 2 are distinct. Rules 1/2 snapshots remain readable; fresh Daily seeds use rule version 2. Existing board, pieces, RNG and locked date remain preserved during migration. QA focus-control metadata is honored only in debug builds with an isolated test save; the rendered harness explicitly tests the production focus-loss policy and audio lifecycle without relying on desktop window activation timing.

## Reliability and teaching in 0.4.1

Save results propagate to a persistent notice outside the replaceable page. Retry remains reachable beneath modal sheets; transient failures retry every five seconds, including while paused. Future-version saves stay read-only and explain that an update is needed. Pause and results only claim successful persistence when the write succeeded. The normal checkpoint accounting remains in memory across failed writes so a later successful retry includes all accumulated deltas without counting a game twice.

Reset stages a checksummed empty envelope in a separate `.reset` file and verifies it before replacing main. Memory and recovery copies remain untouched on staging/commit failure. Only a committed reset clears memory and removes older recovery copies. Uncommitted reset stages are ignored by the ordinary startup loader. Replacement uses Godot's documented file overwrite behavior for [DirAccess.rename_absolute](https://docs.godotengine.org/en/4.6/classes/class_diraccess.html#class-diraccess-method-rename-absolute).

Modal sheets own explicit Back callables; ordinary dialogs dismiss themselves, while final results and lesson completion return home. They no longer infer navigation from a retained session's terminal flag. GameSession.finish records a manual ending, saved in an optional backward-compatible end_reason field; older snapshots still load.

Terminal state and Daily completion persist immediately. Only the result sheet waits for the final visual timeline; gameplay input is already rejected. Reduced motion skips the wait, Back can open results early, and loading a terminal save shows results without replaying an old animation. The tutorial separately earns charge through real line clears from zero, highlights its next two target cells and waits for the fourth clear before preparing the wrapping example. Tutorial boards still never overwrite player runs or statistics. Clear/points/combo messages are no longer replaced by charging instructions or the post-placement refresh; the energy meter provides those instructions independently.
